# Refine Work Item

Turn a GitHub issue into an implementation guide, posted as a comment on that issue, that
`/implement-work-item` can follow without guessing.

**Issue to refine:** `$ARGUMENTS`

---

## Step 0 — Normalize the input

`$ARGUMENTS` is a bare issue number (`8`) or a full issue URL.

- URL → take the numeric id from the end of the path and `owner/repo` from the path.
- Bare number → read the slug from `git remote get-url origin`.
- Empty → ask for the issue number and stop.

Store as `ISSUE_NUMBER` and `REPO_SLUG`.

---

## Step 1 — Gather context

Run in parallel:

1. `gh issue view ISSUE_NUMBER --repo REPO_SLUG --json number,title,body,labels,comments`
2. Read `CLAUDE.md` — it holds the constraints of this repository and is authoritative.
3. Read the specific source files the issue touches. Do not guess at existing structure.

---

## Step 2 — Analyze

Work out, concretely:

- **Which projects are involved**: `Core` (all logic), `UI` (the screens and `AdvisorSession`),
  `Desktop` (the Windows window), `Web` (the macOS host), `Core.Tests`.
- **What types change** — records, services, stores — with their real names and namespaces.
- **What SQLite schema changes** are needed, if any. There is no ORM: a schema change is a
  new migration appended to `Storage/Migrations.cs` (never an edit to an existing one), and
  must carry user data across. See "Database schema" in `CLAUDE.md`.
- **What can be tested without a UI or a database.** Prefer moving logic into `Core` over
  writing a test that needs a rendered component. Tests needing storage use a throwaway
  SQLite file.
- **What the user actually sees** — which control, on which screen.
- **What assumptions** you are making to fill gaps the issue left implicit.

Apply `CLAUDE.md`. The rules most often violated: logic that belongs in `Core` written into
a `.razor` file, and user input reaching a SQL `LIKE` without escaping.

---

## Step 3 — Write the guide

Use exactly this structure. The `<!-- IMPLEMENTATION-GUIDE -->` marker and the `###`
headings are parsed by `/implement-work-item` — do not rename them.

```markdown
<!-- IMPLEMENTATION-GUIDE -->
## 🛠️ Implementation Guide — #[number]: [title]

> Generated by `/refine-work-item`. Consumed by `/implement-work-item`.

---

### Refined Scope
[One or two sentences, more precise than the issue title.]

---

### Assumptions
[Every decision made to fill a gap. "None" if the issue is fully specified.]

---

### Affected Layers
| Layer | Project | Action |
|---|---|---|
| Core | `MtgaCollectionAdvisor.Core` | Create / Modify / None — reason |
| UI | `MtgaCollectionAdvisor.UI` | Create / Modify / None — reason |
| Desktop | `MtgaCollectionAdvisor.Desktop` | Create / Modify / None — reason |
| Web (macOS host) | `MtgaCollectionAdvisor.Web` | Create / Modify / None — reason |
| Tests | `MtgaCollectionAdvisor.Core.Tests` | Create / Modify / None — reason |

---

### Files to Create / Modify
```
[one path per line, tagged [CREATE] or [MODIFY]]
```

---

### Data Contracts
```csharp
// Records, method signatures, SQL for new queries.
```

---

### Validation Rules
[field → rule → behaviour when violated]

---

### Business Rules to Enforce
[Numbered guards and invariants.]

---

### Implementation Order
[Numbered atomic steps: Core → Tests → UI → hosts → verification.]

---

### Test Cases
| # | Test Name | What it validates |
|---|---|---|

---

### AC → Task Mapping
- [ ] **AC1**: [text] → [what to implement]

---

### Prerequisites
[Issue numbers that must land first, or "None."]

---

### Open Questions
[Anything needing a decision from the maintainer, or "None."]
```

---

## Step 4 — Post it

Write the guide to `impl_guide_ISSUE_NUMBER.md` in the repo root using the Write tool with
an absolute Windows path (never `/tmp/` — it resolves differently for the Write tool and for
`gh.exe`). Then:

```bash
gh issue comment ISSUE_NUMBER --repo REPO_SLUG --body-file "impl_guide_ISSUE_NUMBER.md"
rm -f impl_guide_ISSUE_NUMBER.md
```

Report the issue URL, the key decisions, and any open questions that block implementation.
